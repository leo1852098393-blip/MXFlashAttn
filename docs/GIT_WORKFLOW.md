# MXFlashAttn Git 存档规则

## 目的

Git 用来保存每个可恢复的项目状态。后续开发不直接覆盖唯一版本，而是通过
提交记录保留历史。

## 当前重要存档点

- `v1.3.0-public-candidate`：已完成 C500/vLLM 0.17.0 验证的公开候选基线。
- `v1.4.0-dev-start`：后续 Prefill、调度和长上下文工作的开发起点。

这些标签当前只存在于本地，是否推送到远程仓库要单独确认。

## 后续工作顺序

每次修改遵循以下顺序：

1. 先确认工作树状态，确保知道上一次存档在哪里。
2. 只做一个边界清晰的小改动。
3. 运行相关测试或静态检查。
4. 检查差异，确认没有混入凭据、模型权重、实例信息或无关文件。
5. 用清晰的提交说明保存结果。

推荐的提交类型：

- `feat:` 新功能
- `fix:` 问题修复
- `test:` 测试或验证框架
- `docs:` 文档
- `perf:` 性能优化
- `chore:` 工程维护

## 改坏时如何恢复

优先保留现场，再决定恢复方式：

- 只是想查看历史：使用 `git log` 和 `git show`。
- 想回到上一个提交继续开发：从目标提交创建新分支。
- 当前改动还没有提交：先保存为临时提交或暂存，不直接删除。
- 已经确认某次提交有问题：优先新增修复提交，不改写公开历史。

## 本项目的分支约束

- `main` / `v1.3.0` 工作树：作为公开基线，不在其中做 v1.4 开发。
- `dev/v1.4.0`：当前后续优化开发线。
- C500 原始证据放在上层工作区 `02_evidence/`，不提交到公开仓库。
- 没有用户明确确认，不执行 GitHub 或 GitLink push。

## 一个阶段何时提交

满足下面条件时就应建立一次存档：

- 一个小功能已经完成；
- 测试结果已记录；
- 代码和文档状态相互一致；
- 下一步工作可以从这个状态继续。

提交不是最终发布。提交只代表“这个本地状态可以恢复”。

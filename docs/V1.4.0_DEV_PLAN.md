# MXFlashAttn v1.4.0-dev 开发计划

**建立日期**：2026-10-16  
**基线**：v1.3.0 public candidate  
**开发分支**：`dev/v1.4.0`  
**状态**：阶段 A 本地准备完成，等待 C500 实测；未发布，未推送

## 1. 版本定位

v1.4.0-dev 是 v1.3.0 之后的独立开发线。它用于验证下一阶段的
Prefill、调度策略和长上下文稳定性，不改变 v1.3.0 已经冻结的能力边界。

v1.3.0 仍然是当前对外发布和申报材料引用的基线。除非新功能完成真实
C500 验证、回归测试和文档审计，否则不能写入 v1.3.0，也不能作为已完成
能力对外宣传。

## 2. 开发顺序

### 阶段 A：本地正确性和测试框架

- ✅ 建立 Prefill 的 reference/prototype 实现。
- ✅ 增加 CPU 或可用设备上的参考结果测试。
- ✅ 明确张量布局、GQA、causal 和数值容差。
- ✅ 建立长上下文误差统计测试，但不把本地测试结果称为 C500 性能结果。
- ✅ 设计 dispatch policy 接口，默认不启用未经标定的阈值。
- ✅ 固定 C500 实验矩阵、结果 schema 和证据字段。
- ✅ 增加 vLLM 版本识别和非侵入式兼容性 probe。

### 阶段 B：C500 最小实测

- 对 vendor/v7 和 Prefill prototype 做同配置 baseline 对比。
- 测量 TTFT、平均延迟、P95 和显存峰值。
- 标定小 batch、KV 长度和 head dimension 的调度边界。
- 做 16K 长上下文的数值稳定性和真实生成验证。
- 只有在 prototype 有稳定收益时，才进入 C500 专用 Prefill kernel 设计。

### 阶段 C：兼容性评估

- 获取实际 vLLM 0.30 目标环境和接口。
- 先做版本探测、兼容层边界和 mock tests。
- 在真实环境完成接口、正确性和生成验证后，才能标记 vLLM 0.30 支持。

### 阶段 D：后续候选项

FP8 KV cache、Prefix Caching、多卡 TP/SP、跨硬件抽象层和 speculative
decoding 暂不并行实施。它们需要在 v1.4 的核心结果稳定后重新排序。

## 3. 版本验收门槛

### 必须满足

- v1.3.0 基线测试不回归。
- 新增功能有对应的本地测试。
- 每个性能数字都有原始配置、设备、软件版本和 dispatch 证据。
- 未经 C500 实测的阈值只能作为候选配置，不能作为默认生产策略。
- README、CHANGELOG 和结果报告明确区分基线结果与开发结果。

### 不在本版本直接承诺

- 通用跨硬件 FlashAttention。
- 所有 Prefill 场景 30%--50% 加速。
- vLLM 0.30 已兼容。
- FP8 已支持或显存必然节省 40%--50%。
- 多卡 TP/SP 已可用。

## 4. 工作区规则

- 代码只在 `MXFlashAttn_v1.4.0-dev` 工作树修改。
- C500 原始结果放在上层工作区 `02_evidence/`，不放进公开仓库。
- 不自动推送；完成一个可审计里程碑后再单独决定是否发布。
- v1.3.0 工作树作为只读基线，不在其中继续开发。

## 5. 阶段 A 验收记录

阶段 A 已在本地完成。当前测试覆盖 Prefill 原型、GQA、causal、长上下文误差
统计、候选调度策略、实验清单生成和 vLLM 兼容分类。

下一步只剩 C500 实测：运行 `docs/C500_V14_EXPERIMENT_PLAN.md` 中的固定矩阵，
记录真实性能、TTFT/P95、显存、dispatch 和长上下文结果。

## 3. Prefill 原型结论

`run_c500_prefill_prototype.py` 在 C500 上比较 MetaX vendor dense
prefill 与 `prefill_chunked_reference`：

| 场景 | Vendor median | Prototype median | Prototype/Vendor | 最大绝对误差 |
|---|---:|---:|---:|---:|
| batch 1, seq 256 | 0.079 ms | 0.652 ms | 8.21x | 0.001953125 |
| batch 1, seq 512 | 0.089 ms | 1.043 ms | 11.72x | 0.001953125 |
| batch 1, seq 1024 | 0.116 ms | 2.647 ms | 22.80x | 0.001953125 |
| batch 4, seq 512 | 0.104 ms | 2.419 ms | 23.27x | 0.001953125 |
| batch 16, seq 1024 | 0.870 ms | 28.134 ms | 32.34x | 0.001953125 |

结论：原型正确性通过，但它是 Python/ATen correctness-first 实现，不是
C500 优化 kernel。它明显慢于 vendor，因此**不接入默认生产 dispatch**。

## 4. M1 算子级验收

已在新 C500 实例上重新验证：

- 支持配置 `s512`、`gq4`、`d64`：输出与 vendor 对照通过
- `s8192`：所有 split-NP 配置通过，`NP16` 最快约为 vendor 的 `3.60x`
- `bf16`：支持配置 correctness 通过
- `ovf`：UM1 在预期极端溢出输入上出现 NaN；UM2 分桶惰性缩放通过
- GQ=3/5/6/7：binding 明确拒绝，分别记录 `unsupported config`，属于预期 guard

Guard runner 使用 `/opt/conda/bin/python`，避免实例没有 `python` 别名造成误报。

## 6. TTFT/P95 状态

已新增流式测量 harness：`scripts/run_c500_streaming_ttft.py`。在 C500 上用
Qwen3-4B、32 路并发、每路最多生成 128 token 的同口径测试，baseline 和
candidate 都能完整返回增量 token，并取得首 token/完成时间戳。

本地归档结果位于：
`02_evidence/c500_v14_20261017/c500_new_instance/streaming/`

- baseline：TTFT median `116.69 ms`，P95 `117.16 ms`；完成延迟 median
  `2362.98 ms`，P95 `2363.41 ms`。
- candidate harness：TTFT median `162.62 ms`，P95 `163.08 ms`；完成延迟
  median `2388.35 ms`，P95 `2388.82 ms`；32 个请求均完成。
- candidate harness 的 `dispatch_event_count=0`，因此这组 candidate 流式数字
  **不能作为 M1 命中性能证据**。项目已有的同步 `LLM.generate` 真实 vLLM
  证据仍以第 5 节的 M1 dispatch 结果为准。

这说明严格 TTFT/P95 的采集链路已经打通，但当前 vLLM 0.17.0 的
`AsyncLLMEngine` 路径没有复用本项目已验证的同步 adapter 注册路径；在修复
该集成边界前，不把 candidate streaming 结果写成 M1 TTFT/P95 提升。

此前离线 `LLM.generate` 结果中的首 token字段为 `null`，但可用的 wall latency、
tokens/s、显存和同步 candidate dispatch JSONL 已归档。

## 7. 长上下文兼容性边界

此前一次使用项目 adapter、`MXFLASHATTN_GRAPH_OFFICIAL_SPLIT=1` 的真实 C500
16K prefill 试验曾在 MetaX official split wrapper 内返回
`CUDA error: invalid argument`；同一模型和 `max_model_len=16384` 的纯 vendor
路径可以完成生成。该问题在新实例的真实长 prompt 回归中未复现。

v1.4.0 现已在 official split 边界加入窄化回退：当 MetaX wrapper 明确返回
`invalid argument` 时，恢复原始 vendor attention 函数并重试一次；其他异常仍
直接抛出。

真实长上下文回归：

- Qwen3-4B，15,000 prompt tokens，`max_model_len=16384`，生成 32 tokens；
- vendor prefill/official split 成功，`vendor_direct=1188`；
- M1 decode 成功命中 `m1_split_decode=1116`；
- 无 `official_split_invalid_argument_fallback` 事件。

这证明当前 C500/vLLM 0.17.0 组合下，接近 16K 的真实 prompt 可以完成
Prefill + M1 decode；它仍不是 Prefill kernel 的性能证明。

## 8. 最终判断

本轮 C500 工作已完成到 v1.4.0 发布候选的可审计阶段：

1. 环境部署、扩展编译和 79 项测试通过；
2. Prefill prototype 已在真实 C500 上完成正确性和性能定位；
3. M1 Split-KV decode 已在 Qwen3-4B/8B 真实 vLLM 场景复现加速；
4. 8192 上下文、BF16、overflow 和不支持 GQA guard 已有原始证据；
5. head_dim=256 fallback 已在 Qwen3.5-9B 真实生成中验证；
6. TTFT/P95 和严格 token-level 长尾一致性仍未形成完整结论；
7. 接近 16K 的真实长 prompt 已完成 vendor prefill + M1 decode 回归；
   fallback 保护保留为异常边界，不计入性能提升。

因此，v1.4.0 当前可以作为**完成 C500 验证的发布候选版本**继续整理申报
材料，但不应把 Prefill prototype 写成生产加速，也不应把小样本文本匹配
写成严格逐 token 一致性证明。PyPI 发布继续延期到材料和发布策略最终确认后。
